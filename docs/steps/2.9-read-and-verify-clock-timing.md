# Step 2.9: Read and verify the maximum-clock estimate

Recorded November 14, 2026. The feasible candidate's saved routed timing is
checked and documented. The two-architecture checklist item remains partial:
the fully layer-pipelined candidate exceeds capacity and has no routed Fmax.

## What we found

The corrected head-pipelined design has a **19.3858566 MHz estimated Fmax**
in the routed report saved during [step 2.8](2.8-place-and-route.md).
Its required clock remains **12 MHz**. We checked the existing evidence;
we did not rerun placement/routing, sweep clock constraints, or measure a board.

| Quantity | Result | Meaning |
|---|---:|---|
| Operating clock | 12 MHz | Board clock used by the generated design |
| Routed estimated Fmax | 19.3858566 MHz | Estimate for this particular placement and routing |
| Estimated minimum period | 51.584 ns | Time budget corresponding to that Fmax |
| Required period | About 83.333 ns | Time available at the 12 MHz target |
| Arithmetic period margin | About 31.749 ns | Required period minus estimated minimum period |

The report's constraint is 12.0000477 MHz because of tool numeric precision.
It agrees with the nominal 12 MHz setting. The period margin above is arithmetic
from the clock estimate, not a separately reported slack analysis.

## A simple example

A 12 MHz clock gives the circuit about 83.33 ns between clock edges.
The slowest synchronous path needs about 51.58 ns according to the tool.
Since 51.58 is less than 83.33, this routed implementation passes that target.

The conversion is `period in ns = 1000 / frequency in MHz`.
The 19.39 MHz estimate is not an instruction to change the oscillator or UART
clock: the UART divider was generated for 12 MHz.

## Where the time goes

The synchronous critical path starts at the core's **input register**, passes
through unregistered gate logic and score summation, and ends at a **score
register**. The named endpoint in the routed report is under `sc_reg[6]`.
The input register named `l0` is not a learned logic-layer register.

| Path component | Delay (ns) |
|---|---:|
| Register clock-to-output | 1.390 |
| Routed connections | 33.865 |
| Combinational logic | 15.505 |
| Destination register setup | 0.824 |
| Total | 51.584 |

Routed connections contribute a substantial part of the delay. Adding pipeline
registers might change it, but the full-layer candidate does not fit this FPGA.
This observation alone does not identify an optimal architecture.

The report also lists asynchronous input-to-register and register-to-output
paths, about 7.247 ns and 14.453 ns respectively. We retain them separately.
They do not determine the same-clock Fmax and do not certify asynchronous I/O
timing, external devices, or synchronizer reliability.

## How we made the report trustworthy

The new [report_timing.py](../../scripts/report_timing.py) command reads a saved
implementation without changing its original validation record:

1. Require the successful attempt status and all nine recorded input/output
   file hashes. Preserve the historical tool identity from the saved record.
2. Verify that the synthesis manifest still matches the routed input and that
   the parent export's parameters match the archived parameter hash.
3. Check the target/package, completed implementation flags, placed cells,
   capacity, successful log, and single positive finite clock result.
4. Select the same-clock rising-edge path explicitly. Sum its delay categories
   and cross-check the result against `1000 / Fmax`.
5. Write a compact JSON summary with units, provenance and limitations.

The parameter hash matters because a later export could replace `params.json`
next to an older route. The older route must not inherit the new settings.
The routing log also contains an earlier 19.18 MHz estimate; the command uses
the final routed JSON result instead of the first frequency line in that log.

## Reproduce the evidence check

From the repository root, with the local step 2.8 artifacts available:

```bash
.venv/bin/python scripts/report_timing.py \
  runs/digits_w1000/uart_comb_head/implementation.UVAx2g \
  --out docs/results/step-2.9-timing.json
```

The saved independent step 2.8 route, `implementation.ogVBqL`, produces the same
Fmax and path-delay breakdown. Neither check requires an installed FPGA tool
executable; the reader uses the recorded provenance.
The older independent route has no executable fingerprint in its validation
record. Its summary explicitly marks tool identity unavailable; the primary
`implementation.UVAx2g` record retains the resolved executable path and SHA256.

Raw `runs/` files are gitignored. The tracked [timing summary](../results/step-2.9-timing.json)
and [step 2.8 results](../results/step-2.8-results.json) preserve the reported
numbers and hashes. A fresh clone needs the raw artifacts or a reproduced
implementation before it can revalidate those hashes. See step 2.8 for the full
export/synthesis/implementation commands.

The fully pipelined candidate is deliberately rejected by this reader because
its attempt status is `failed (exit 3)`. Its 6,575 required logic cells exceed
the UP5K's 5,280; no clock estimate is substituted for the missing routed result.

## Debug report: older validation metadata

- **Expected:** the reader can summarize the older independent archive while
  keeping any missing tool identity visible.
- **Actual:** the first check exited with `Timing report rejected: 'nextpnr'`.
- **Reproduction:** run `scripts/report_timing.py` on `implementation.ogVBqL`.
- **Root cause:** the initial reader required an executable-fingerprint field
  added after that archive's validation record was created.
- **Fix:** retain its file-hash checks, write `nextpnr: null`, and add an explicit
  limitation for that older record. Never fill the gap with today's executable.
- **Verification and prevention:** rerun both saved archives and include an
  independent regression for older records without that optional field.

## Verification and research direction

The [independent review](../reviews/step-2.9-independent-review.md) checks the
code, raw timing, units, hashes and failure handling. It includes rejection
tests for altered or inconsistent evidence. No RTL or training behavior changed
in this step. The verifier's 18 new report cases pass; the full suite passes
**63 tests** in 10.62 seconds, with no skipped cases in that run.

This is useful engineering evidence for choosing a feasible implementation and
holding its clock fixed in later experiments. It establishes no power or energy
improvement, physical maximum clock, or research novelty. Comparisons must still
use matched targets, architectures, clocks, input sequences and useful work.
