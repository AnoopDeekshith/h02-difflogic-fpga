# Step 2.8: Place and route the FPGA design

Recorded November 14, 2026. The corrected candidate has completed placement,
routing and tool timing validation. The fully layer-pipelined alternative is
still too large; the complete two-architecture checklist item remains partial.
All commands ran locally on the Mac, without a physical FPGA or Codespaces.

## Why we needed this

[Step 2.7](2.7-clock-and-pin-constraints.md) counted packed cells. Now we need to
put those cells in actual FPGA locations and connect them using available
routing. Only then can the tools estimate whether signals arrive before the
next clock edge. Fitting the cell count alone does not establish this.

## What happened first

We routed the original UART design at the board's **12 MHz** target. Routing
completed, but timing failed: the estimated maximum clock was **7.26 MHz**.
The long path passed through the logic network, score sums and class selection.
We kept this failure as evidence rather than changing the clock requirement.

## How we fixed it

We added an optional `--head-pipeline` architecture:

1. Keep the same trained gates and connections.
2. Store the ten class scores in a small register bank.
3. Select the winning class with a balanced comparison tree.
4. Delay scores and the valid signal consistently with that extra stage.

The core now has **3 register stages**, versus the old value of 2. From the
input capture edge, output availability is after two elapsed periods and a
downstream register can capture it after three. See [step 2.10](2.10-compare-latency-and-throughput.md)
for the measured boundaries. We did not register all 4,000 neurons.

For example, instead of comparing ten classes one after another, compare pairs,
then compare the pair winners. Equality always keeps the lower class index.
Both the returned scores and the winner use the same stored score bank.

The verifier also found that receiving each UART byte changed the core input.
We added a separate completed-image register. The network now sees an atomic
new image only after the full packet arrives. This avoids partial-image activity
being mistaken for useful inference work. It does not eliminate clock power or
make a slow UART workload equivalent to a fully utilized inference core.

## Results

| Candidate | Outcome |
|---|---|
| Historical original UART design | Routed, but failed 12 MHz timing: 7.26 MHz estimate |
| Corrected head-only pipeline plus atomic image input | Routed; **4,160/5,280 logic cells**, **19.39 MHz estimated maximum**, passes 12 MHz |
| Current full layer pipeline plus head pipeline and atomic input | **6,575/5,280 logic cells**; rejected before routing |

The corrected head-only candidate synthesizes to **3,449 LUT4s, 911 flip-flops
and 167 carry cells**. The full candidate has 5,045 LUTs and 4,166 flip-flops;
packing explains why those separate numbers still cannot fit the device.
These candidates differ in more than one implementation detail, so this table
is a feasibility record, not an isolated scientific speedup experiment.

The working design passed **450/450 UART images**, checking every integer score
and predicted class. A synthesized iCE40-cell functional simulation also passed
12 images at the hardware UART divider and timeout. This latter simulation has
no routed delays; it is not a glitch measurement or post-route timing simulation.

## How we checked the evidence

- Every implementation attempt gets a fresh output directory and a terminal
  status file. A failed attempt cannot reuse old successful output files.
- Synthesis fingerprints the source files, parameters and mapped netlist.
  Modified or outdated files require a fresh export/synthesis.
- The result validator checks the FPGA target, pack/place/route completion,
  assigned cells, capacity, clock result, ASC file and routing log.
- Input/output SHA256 hashes and tool identity are saved with the result.
- The full suite passed **45 tests**, including rejection of deliberately
  broken evidence, stale inputs, incorrect clocks and invalid synchronizers.

The independent verifier reran the real implementation and obtained the same
19.39 MHz / 4,160-cell result. It also added 16 exhaustive tests covering
16,384 synthetic inputs with odd class counts, ties and both pipeline modes.
Those 16 tests are included in the suite; they are not additional unique tests
on top of the 45. See the [independent review](../reviews/step-2.8-independent-review.md).

## Reproduce the working candidate

From the repository root:

```bash
.venv/bin/python scripts/export_uart.py runs/digits_w1000 --head-pipeline --sim-clks-per-bit 8
bash sim/run_sim.sh runs/digits_w1000/uart_comb_head
bash synth/synth_uart_ice40.sh runs/digits_w1000/uart_comb_head
bash synth/implement_uart_ice40.sh runs/digits_w1000/uart_comb_head
.venv/bin/python scripts/simulate_mapped_uart.py runs/digits_w1000/uart_comb_head --n 12
.venv/bin/python -m pytest tests -q
```

The fast UART testbench divider does not change the hardware divider. The
mapped-cell check uses the actual 104-clock divider. `latest_attempt.txt`
identifies the latest attempt; `latest_success.txt` identifies the last success.
Read the attempt's `status.txt` before interpreting it. Raw files remain in
gitignored `runs/`; the [compact results record](../results/step-2.8-results.json)
preserves the reported numbers and hashes in source control.

## Are we heading in the right research direction?

Yes, as an experiment to test, not an established energy-saving result. The
review required two methodological corrections that we made:

- New training runs use a separate validation partition for epoch monitoring,
  save split indices/checkpoints, and evaluate test accuracy at final evaluation.
  Select penalty settings using validation. The old digits test has already
  been inspected, and its old full-training-pool baseline is exploratory.
  Retrain both baseline and penalized models under the same new protocol.
- The activity term is labeled an IID, zero-delay training surrogate, not SAIF
  activity or power. The same images in a different order produce different
  switching, so future comparisons must freeze the workload and image order.

Prior work already covers hardware-aware DLGN training and differentiable
switching-power optimization. A possible narrower contribution is testing DLGN
gate-rule learning against mapped/measured FPGA energy at comparable accuracy.
Novelty and energy benefits still need evidence. The review links the primary
papers and sets out the controls for a fair comparison.

## What this does not prove

We have not programmed a board, measured electrical power, demonstrated lower
energy, proved equivalence for every input, or certified synchronizer MTBF.
The routed clock estimate is not a measured board clock limit. A supported
device-specific power flow or actual rail measurements are still required.
