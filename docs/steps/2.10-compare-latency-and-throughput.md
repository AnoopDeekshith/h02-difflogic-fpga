# Step 2.10: Compare latency and throughput

Recorded November 15, 2026. We measured cycle boundaries in RTL simulation and
combined them with the saved implementation evidence. The feasible candidate
has a complete scoped report. The two-architecture hardware comparison remains
partial because the full-layer pipeline cannot fit this FPGA.

## What we did and why

[Step 2.9](2.9-read-and-verify-clock-timing.md) established how to read and check
the routed clock estimate. Now we distinguish three different questions:

1. How long after capturing an image does the core present its result?
2. How often can a directly driven core accept another image?
3. How long does the UART board interface take to receive an image and return
   the full result?

The distinction matters for the later energy experiment. A core supplied every
clock has a different workload from one waiting for serial packets.

## Results

Both candidates use the same trained 4-layer, 1,000-gate-per-layer model and the
same ordered inputs. Both have the score-register head pipeline and atomic
UART input commit introduced in [step 2.8](2.8-place-and-route.md).

| Quantity | Head pipeline | Full layer plus head pipeline |
|---|---:|---:|
| Packed logic cells | 4,160 / 5,280 | 6,575 / 5,280 |
| Implementation | Routed; meets 12 MHz | Exceeds capacity |
| Estimated routed Fmax | 19.3858566 MHz | Unavailable |
| Register stages (`LAT`) | 3 | 7 |
| Input capture to output availability | 2 clock periods | 6 clock periods in RTL simulation |
| Input capture to downstream register capture | 3 clock periods | 7 clock periods in RTL simulation |
| Core initiation interval | 1 clock period | 1 clock period in RTL simulation |
| Cycle-equivalent output latency at qualified 12 MHz | 166.67 ns | Unavailable |
| Cycle-equivalent downstream capture at qualified 12 MHz | 250 ns | Unavailable |
| Calculated standalone core interface capacity | 12 million images/s | No timing-qualified rate |

The 12-million figure is `12 MHz / 1 clock per accepted input`. It describes the
standalone generated core's interface capacity, supported by cycle simulation
and the containing design's 12 MHz timing result. It is not measured board
throughput. The existing UART wrapper cannot feed that interface every clock.

The full candidate's RTL can still be simulated to determine cycle counts.
That does not establish that it can operate at 12 MHz on the UP5K, so its
qualified nanosecond values and rates are deliberately `null` in the report.
We do not use the 19.39 MHz estimate to claim operation at a higher board clock.

## Why three stages means two elapsed clock periods

Earlier notes used `LAT` as a shorthand for latency. It counts register stages.
The more precise definitions are:

| Edge | What happens for the head-pipelined core |
|---|---|
| 0 | Input register captures the image and valid input |
| 1 | Score registers capture the calculated scores |
| 2 | Output registers present scores, class and valid after the edge |
| 3 | A downstream register can capture that result at its clock edge |

There are **two elapsed periods from edge 0 to edge 2**. At 12 MHz, each period
is about 83.33 ns, giving 166.67 ns to output availability. A downstream receiver
captures the result at edge 3, giving 250 ns to that boundary.
These nanosecond values are cycle-based equivalents, not measurements of
physical output-arrival time. Ordinary RTL simulation does not include routed
propagation or register clock-to-output delays.

The RTL, model, pipeline depth and valid behavior have not changed. We corrected
the reporting terminology and exporter messages. The parameter name `LAT` stays
compatible with existing exports and testbenches.

Latency and throughput are different. Like an assembly line, the core can have
multiple images in flight: a new image enters every clock even though each
image passes through several register stages.

## What the UART actually permits

The board receives **26 request bytes** and returns **13 reply bytes**. Each
8N1 byte uses 10 serial bits. The actual hardware divider is **104 clocks per
bit** at 12 MHz, giving approximately 115,384.6 baud. We did not use the faster
8-clock testbench divider for these measurements.

For the working head-pipelined candidate, three checked transactions gave:

| Measurement boundary | Result |
|---|---:|
| First request start bit to end of the last reply stop bit | 40,528.5 clocks |
| That transaction interval at 12 MHz | 3.377375 ms |
| Request-start spacing with the benchmark's immediate ideal host | 40,529 clocks |
| Calculated rate for that ideal-host simulated workload | About 296.08 images/s |

The half clock is real within the bench's phase convention: the host starts a
request on a falling edge, while the FPGA transmitter completes on a rising
edge. The next request starts on the next falling edge. This is an explicit
testbench workload, not a universal minimum host delay.

USB buffering, operating-system scheduling, serial-client behavior and physical
board effects are absent from the simulation. Actual host-to-board performance
still needs measurement.

Simply adding all 39 byte times gives `39 × 10 × 104 = 40,560 clocks`, or 3.38 ms.
This is a **nominal sum of serial work in the two directions**, not a strict
wall-time lower bound. The receiver recognizes the last request's stop bit
around its midpoint, so the reply can begin while that stop bit is still on
the other wire. Our benchmark checks the full final reply stop bit rather than
ending at the reply decoder's earlier valid pulse.

The full-layer candidate produces a simulated request/reply interval of
40,532.5 clocks and request spacing of 40,533 clocks. These are cycle-model
observations only; its physical time and rate stay unavailable because it
cannot be implemented on this target.

## How we measured and checked it

The new [report_performance.py](../../scripts/report_performance.py) command:

1. Checks synthesis freshness and binds each export to its archived route or
   explicit capacity-failure evidence.
2. Regenerates the core from `model.json` and requires an exact RTL match.
3. Generates fresh NumPy reference scores and classes from the saved inputs.
4. Runs [tb_performance.sv](../../rtl/tb_performance.sv) in a fresh attempt folder,
   streaming 32 core vectors and checking 3 complete UART transactions per
   candidate. Every score and predicted class must match the reference.
5. Separately checks output availability, downstream capture and consecutive
   output spacing. The UART measurement uses the full hardware divider.
6. Requires matching model/input hashes and packet settings across the comparison.
7. Records model, input, source, vector, bench, simulator and log fingerprints.

The simulation clock's arbitrary 10 ns period is a cycle-counting convenience.
It does not prove 100 MHz hardware operation. Conversion to physical time uses
the qualified 12 MHz target and is withheld for the oversized candidate.

The [independent review](../reviews/step-2.10-independent-review.md) documents
separate streaming, bubble, UART-boundary and production-bench tests. Its
independent cycle bench covers all four layer/head register configurations,
including odd class counts and changing invalid input data.
The full regression suite passes **71 tests in 15.14 seconds**, with no skips.
The 8 new independent performance cases are included in that count.

## Debug report: premature reply completion in the benchmark

- **Expected:** count all 13 reply bytes and finish after the full last stop bit.
- **Actual:** the first benchmark stopped with `Missing reply bytes`.
- **Reproduction:** the initial bench waited for adapter `DRAIN` state and
  transmitter `ready` together; the failed run is preserved under
  `runs/digits_w1000/uart_comb_head/performance.ygvi6bc5/`.
- **Root cause:** state and transmitter counters update through separate
  nonblocking assignments. A transient delta-cycle combination looked like
  completion when the last byte was starting.
- **Fix:** observe `DRAIN`, then the last byte being busy, then its transition
  back to ready. No FPGA RTL was changed.
- **Verification:** both trained candidates complete all reference comparisons;
  independent tests compile and exercise the shipped benchmark itself.
- **Prevention:** retain those full-stop-bit regressions and explicit endpoints.

## Reproduce

From the repository root, with the step 2.8 local artifacts and Icarus installed:

```bash
.venv/bin/python scripts/report_performance.py \
  runs/digits_w1000/uart_comb_head \
  runs/digits_w1000/uart_comb_head/implementation.UVAx2g \
  --comparison runs/digits_w1000/uart_pipe_head \
  runs/digits_w1000/uart_pipe_head/implementation.1iiA0a \
  --out docs/results/step-2.10-performance.json

.venv/bin/python -m pytest tests -q
```

The tracked [performance summary](../results/step-2.10-performance.json) stores
the results and fingerprints. Raw `runs/` artifacts remain gitignored; a fresh
clone needs those artifacts or a reproduced export/synthesis/implementation.
The self-contained regression tests can run without the trained run artifacts.

## Research direction and limits

This step provides a useful workload boundary for subsequent activity and
energy experiments. It establishes neither lower power nor lower energy.
Do not divide UART-workload power by the standalone core's 12-million-image/s
capacity to calculate energy per prediction. Count completed predictions within
the actual power-measurement window and use that workload's achieved rate.

No physical board was programmed, no electrical measurement was performed, and
no universal equivalence or research novelty is established. The capacity
failure remains a reported limitation, not a fabricated second hardware result.
Later baseline/penalty comparisons need matched training partitions, target,
clock, architecture, ordered inputs and useful-work windows.
