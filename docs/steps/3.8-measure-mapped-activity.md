# Step 3.8: Measure mapped hardware activity

Status: complete; independently verified.
November 16, 2026.

## Why count mapped signals

The logical gate total in [step 3.7](3.7-cross-check-numpy-and-rtl-activity.md)
answers a narrow question: how often do the four learned layers change across
neighboring saved images? Synthesis can merge, duplicate, or restructure logic,
and the hardware also has registers, carry cells, clocks, and control signals.
Counting mapped net bits gives a second view of activity in the synthesized
design.

This is a digital switching proxy. It does not estimate joules, include physical
glitches, or show that an activity reduction saves energy.

## What this step measures

The planned capture starts from the archived step 3.3 baseline inputs, RTL,
model, and input order. It performs a fresh standalone **head-only core**
`synth_ice40 -device u` mapping, explicitly selecting iCE40 UltraPlus, using the
nominal 12 MHz period of 83,334 ps and initiation interval one. Installed Yosys
0.63 otherwise defaults this flow to the HX device family. The explicit device
setting makes this a distinct mapping protocol from the historical board map,
which did not explicitly select UltraPlus. This is a new synthesis result; it is not a
fresh place-and-route run and does not establish timing, Fmax, or device
capacity. The previous routed UART board design is a different top and is not
the subject of this measurement.

The analysis instruments a canonical vector containing one bit for every
sorted, unique numeric Yosys net-bit ID connected to a top-level port or cell
port. Numeric IDs represent net bits in Yosys JSON. A bit that appears through
multiple named aliases is therefore counted once. String constants are not
instrumented. See the [Yosys JSON documentation](https://yosyshq.readthedocs.io/projects/yosys/en/v0.63/cmd/index_backends.html).

Mapped bits are assigned to disjoint driver categories: LUT outputs, carry
outputs, flip-flop Q outputs, and the primary inputs split into clock (`clk`),
control (`rst`, `in_valid`) and data (`x`), so clock toggles do not inflate
input-data activity. The
whole-trace capture is retained for diagnosis. The finite-workload window is
planned as `(first_drive - 1 ps, last_output_check]`, preserving all 450
inferences including pipeline fill and drain. Raw X/Z changes are reported
separately from known-value flips.

## How the capture and analysis work

1. The capture command checks the archived baseline capture and its provenance,
   then synthesizes the standalone head-only core with `synth_ice40 -device u`
   to a fresh Yosys JSON netlist.
2. It prepares a simulation model from the mapped netlist using functional,
   zero-delay cells. No timing or delay flags are applied.
3. The same ordered 450 saved inputs are replayed at the nominal 12 MHz period,
   with initiation interval one. Scores and predicted classes are checked
   against the NumPy reference, including lowest-index tie breaking.
4. The analyzer builds the unique net-bit vector from top and cell ports,
   assigns driver categories, and counts known flips and X/Z changes for the
   whole trace and the finite-workload window.
5. Capture inputs, source files, tool versions, generated netlist and analysis
   outputs are recorded so the run can be audited. The analysis command reads
   the new capture; it does not reuse an older routed-board waveform as fresh
   mapped evidence.

Startup initialization is a modeling caveat: the mapped simulation sets
`SB_DFF_INIT=0`, while the RTL registers are otherwise uninitialized. Initial
unknowns and subsequent known-value transitions must remain visible in the raw
record; they must not be silently counted as ordinary 0-to-1 or 1-to-0 flips.

## Example: aliases count once

Suppose a net bit with numeric ID `42` is named both `score[0]` and `debug_copy`.
The canonical vector contains ID `42` once, so the same underlying bit does not
inflate the mapped activity count. Two different numeric IDs remain two bits,
even if their values happen to match throughout this workload.

## Reproduction

```bash
.venv/bin/python scripts/capture_mapped_activity.py capture runs/digits_w1000/baseline-waveform.xs90rtvt
.venv/bin/python scripts/capture_mapped_activity.py analyze runs/digits_w1000/mapped-activity.57fn0ze0
.venv/bin/python -m pytest tests/test_mapped_activity.py -q
```

The capture takes about 13 seconds. Each command writes a fresh folder.

## Evidence

Final capture: `runs/digits_w1000/mapped-activity.57fn0ze0/result.json`
(reanalyses `mapped-analysis.e2jmy70l/` and independent `mapped-analysis.s8y33n7i/`).

- Mapping: 2,912 `SB_LUT4`, 339 flip-flops (334 `SB_DFF`, 5 `SB_DFFSR`),
  123 `SB_CARRY`; 3,569 unique net bits.
- All 450 images match NumPy scores and classes (ties to lowest index).
- Whole trace: 667,463 known flips, 0 X/Z changes. By driver: LUT 569,566,
  FF 51,053, carry 23,856, data input 22,071, clock 914 (2 × 457 edges),
  control 3.
- Complete burst `(250001, 37875304]` ps: 667,290 known flips.
- `max_bus_records_per_tick = 1`: Icarus writes one value per identifier per
  timestamp, so these are settled per-timestamp changes, not intra-timestamp
  events.

Code-review fixes (Nov 16): source hashes taken before copying and rechecked;
`yosys-config`/`vvp` from the same install as `yosys`/`iverilog`; window-start
and port-width validation; separate clock/control/data input categories.
The verifier rebuilt the bit list from raw JSON and matched every bit's counts.
See the [independent review](../reviews/step-3.8-independent-review.md).
Known minor items: the `validate_port_bus` docstring still mentions multiple
events per timestamp, and `yosys-config` has no version flag (path and hash
identify it).

The existing step 3.7 result remains a separate logical-gate metric: 628,169
settled layer-output changes over 1,796,000 gate/image-pair opportunities.
Mapped net-bit counts use a different signal population and must not be
substituted for or described as a new value for that logical metric.

## Limits and research direction

- **Correctness:** the intended functional check covers these 450 saved inputs;
  it is not formal equivalence over all possible inputs.
- **Activity proxy:** the mapped trace is from zero-delay functional simulation.
  It does not include timing-driven hazards or physical glitches. Step 3.9
  addresses glitch activity separately.
- **Energy:** no power or energy denominator is measured here. Lower digital
  flip counts, if observed, would not alone demonstrate lower energy. The
  project's later power/energy work remains pending.
- **Physical implementation:** standalone synthesis is distinct from the
  routed UART board top. This step makes no new timing, Fmax, placement, route,
  or capacity claim.
- **Research claim:** this baseline measurement does not establish a benefit
  from activity-aware training or novelty. Comparative models need matched
  splits, target, architecture, clock, and input sequence, with settings
  selected on validation data.
