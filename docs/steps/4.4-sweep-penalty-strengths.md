# Step 4.4: Sweep penalty strengths

Status: complete; independently verified ([review](../reviews/step-4.4-independent-review.md)).
Recorded November 18, 2026.

## What we learned

Among eight declared penalty strengths, **lambda 0.3** had the lowest settled
validation switching that satisfied our accuracy allowance. Compared with the
matched lambda-zero control, it had **17.17 percent fewer logical changes**
while recognizing **two fewer of 270 validation images**, an accuracy loss of
**0.74 percentage points**.

This is an accepted **single-seed validation proxy tradeoff** under the frozen
rule. It is a provisional choice for repeated-seed testing, not a final paper
model or evidence of lower FPGA energy.

## Why we tried several strengths

[Step 4.3](4.3-run-the-initial-penalty-experiment.md) found that lambda 0.1
reduced settled switching but lost too much accuracy. One unsuccessful strength
does not tell us how other strengths behave. A **sweep** means comparing a
declared set of values while holding the rest of the experiment fixed.

The grid was **0, 0.001, 0.003, 0.01, 0.03, 0.1, 0.3 and 1**. It includes
smaller and larger penalties around the first experiment. We chose this grid
after seeing step 4.3, then saved it before obtaining the six new results.
This is disclosed validation-guided development, not a globally blind
preregistration made before any results were known.

The control and lambda 0.1 results were explicitly **reused from verified step
4.3 archives**. The other six strengths were new 60-epoch runs. Reuse avoids
unnecessary retraining, but these two rows must not be called fresh runs.

## Matched procedure and selection rule

Every model used digits, four layers of 1,000 gates, tau 10, batch size 100,
Adam learning rate 0.01, model seed zero and split seed zero. The split remained
1,077 training, 270 validation and 450 deferred-test images. Execution used CPU
with OMP and MKL thread limits of one. All checkpoints were from the **final
epoch 60**, without best-epoch selection or early stopping.

The [step 4.10 policy](4.10-prepare-validation-only-selection.md) permits at
most **one percentage point of hard validation accuracy loss** relative to the
matched control. This working tolerance was unchanged and is not a professor
mandate. Among eligible models, choose lowest switching, then highest accuracy,
then lowest lambda, then model hash. The control remains a selectable option.

No run performed test inference or saved test inputs/labels; test metric fields
remain null. All declared points, including rejected ones, appear in selection.
The historical 93.56-percent test baseline is a different protocol and is not
this sweep's control.

The control sets an accuracy floor of **91.2222 percent**. With 270 validation
images, a candidate needs at least **247 correct**. Lambda 0.3 meets that floor;
lambda 0.1 and lambda 1 do not.

## Understand the selected result with actual counts

NumPy records each gate's hard output for every validation image. There are
4,000 learned gates and 269 adjacent-image pairs, giving:

```text
4000 × 269 = 1,076,000 opportunities for a bit to change
Control:      373,910 / 1,076,000 = 0.34750000
Lambda 0.3:   309,698 / 1,076,000 = 0.28782342
```

That is **64,212 fewer changes**: `64212 / 373910 × 100 = 17.1731 percent`
relative reduction. Accuracy changes from 249 to 247 correct, giving
`2 / 270 × 100 = 0.74074 percentage points` of loss.

Lambda 1 reduces logical changes by **42.30 percent**, but loses 13 correct
images, or 4.81 percentage points. It is retained as a rejected tradeoff, not
promoted because its switching number looks attractive.

Larger lambda does not guarantee monotonically lower measured hard switching:
lambda 0.001 is slightly higher than the control. The training objective uses
soft batch outputs, while this measurement uses fixed hard rules. We observed
the nonmonotonic result; this experiment does not establish its detailed cause.

## Evidence and reproduction

Evidence is `runs/step4.4-sweep.zlmbqzyd/`. Its prewritten `plan.json` contains
the grid, six exact training commands, reused-run fingerprints, thread limits,
source hashes and selection command. `source/` snapshots eight Python files;
`selection_policy.json` preserves the frozen policy. Each new `lambda_*`
directory retains model, checkpoint, protocol, ordered validation data,
scores/classes, metrics, manifest and status. Separate logs and `selection.json`
preserve execution and the decision. Historical and reused artifacts were not
overwritten.

The [tracked summary](../results/step-4.4-penalty-strength-sweep.json) records
every point and its provenance. Raw runs remain gitignored and need separate
archival. To reproduce training, inspect `plan.json` and run its six commands
with **new output directories**, preserving code and policy first. Do not rerun
them into the primary evidence directory or `runs/digits_w1000`.

To recheck selection without retraining, use the plan's `selection_command`
with a new `--out`, for example `/tmp/h02-step44-selection-check.json` if it
does not exist. The selector refuses an existing output file. This checks the
saved models; it does not create a fresh training result.

The [independent review](../reviews/step-4.4-independent-review.md) records a
separate audit, reproducible with:

```bash
.venv/bin/python runs/step4.4-review.independent/audit.py
```

## Verification scope and next step

Independent scalar truth-table evaluation matched all eight models' validation
scores, lowest-index classes and exact change counts: **2,160 image
computations**. Checkpoints showed final epoch 60 and **660 Adam updates** per
parameter. Matched final CPU RNG states, source/policy snapshots, manifests,
data identities, logs and ranking passed. Final documentation review passed with no blocking finding. No executable code changed; the latest 285-test suite result belongs
to step 4.10 and is not a fresh step 4.4 test run.

One validation seed cannot establish repeatability or statistical general
benefit. No test evaluation, new RTL equivalence, resource, fit, timing,
mapped/glitch activity, power, energy or novelty evidence is supplied here.
The previously inspected digits test remains exploratory.

The pending VCD parser/validator consolidation is a separate nonblocking
follow-up before large hardware-activity batches. This NumPy-only sweep does
not use that code, and this step does not claim it was refactored.

before promoting this provisional choice to a stronger research conclusion.
