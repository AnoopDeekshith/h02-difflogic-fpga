# Step 3.7: Cross-check NumPy and RTL activity

Status: completed and independently verified.
November 16, 2026.

## Why compare values before totals

Two different sequences can have the same number of bit changes. For example,
`00 → 01 → 00` and `00 → 10 → 00` both contain two changes, but different bits
switch. An average alone cannot detect swapped wires or the wrong gate order.

This step checks every settled value, the exact changing-bit mask for every
adjacent image pair, and each learned gate's change count. NumPy remains the
reference. Matching totals are a consequence of matching these details.

## What changed

Added [compare_activity_numpy.py](../../scripts/compare_activity_numpy.py).
It reanalyses an existing step 3.3 capture without changing the historical
model, RTL, saved input order, clock, timing constraints or older analysis
sources. A fresh analysis directory is not a new simulation or implementation.

The supported workload remains standalone streaming: all 450 historical saved
images, initiation interval one, nominal 12 MHz with a rounded 83,334 ps period,
three reset cycles and held final input during drain. It is not UART traffic.
The full layer-pipelined hardware candidate remains over UP5K capacity; toy
simulations of that register configuration do not establish physical fit.

## How the comparison works

1. Verify the passed capture manifest and required artifact hashes. Regenerate
   the supported exporter structure in memory and compare it with the archived
   RTL and parameters before assigning stage timing.
2. Load archived `model.json` and `x_test_bits.npy`. Require binary NumPy input
   values with the exact image count and input width. Check model connection
   bounds and gate IDs. Recompute NumPy layer outputs, integer scores and
   predicted classes with [hard.py](../../dlgn/hard.py).
3. Verify every archived input/reference hex word against this fresh NumPy
   computation. Column `j` of the Boolean input/layer array is RTL bit `j`.
   Class `k` occupies score bits starting at `k × SW`. NumPy `argmax` chooses
   the first maximum, preserving the lowest class index on ties.
4. Revalidate the step 3.5 clock, reset, input/valid/marker schedule, held drain
   and stage-aligned windows. Each observation retains the same 450 image
   states and 449 image pairs, shifted for its register availability.
5. Compare known settled RTL values with NumPy at every observation/sample.
   Retain mismatch counts and the first eight detailed discrepancies per
   observation, including image/time/expected/actual/differing bit indices.
   Sampled X/Z values fail; they are not converted to zero.
6. For each adjacent pair, compare XOR masks bit for bit, then compare totals,
   rises/falls and per-gate counts. Repeated inputs still contribute valid
   neighboring-image pairs, even when no bits change.
7. Count recorded events separately within each aligned window, retaining
   intermediate known and X/Z changes. Save full expected/observed settled
   hex sequences and sample times, source copies, environment versions and
   provenance. Recheck capture/source stability before a passed result.

The state comparison covers `x`, input register `l0`, every `lD_c` and `lD`,
score-bank/score view `sc_flat`, winner `best`, registered scores and class.
Only **`l1_c`–`l4_c`** enter the learned gate-output metric. Copies and registers
are checked for correctness but do not double that denominator.

## Baseline result

All 14 observations match for all 450 images. There are **zero mismatched
sample bits, zero mismatched transition bits and zero per-gate count differences**.
The six images with tied maximum scores retain the lowest-index winner.

| Canonical layer | NumPy changes | RTL settled changes | Difference |
|---|---:|---:|---:|
| `l1_c` | 126,546 | 126,546 | 0 |
| `l2_c` | 144,016 | 144,016 | 0 |
| `l3_c` | 167,436 | 167,436 | 0 |
| `l4_c` | 190,171 | 190,171 | 0 |
| **Logical gate-output metric** | **628,169** | **628,169** | **0** |

This gives **628,169 / (4,000 × 449) = 0.34976002227171493 changes per gate
per image pair**, with 314,079 rises and 314,090 falls. This confirms the
settled-count result from step 3.6 using actual NumPy layer states, rather than
only comparing it with the older rounded software average.

Across all observations the checker compares 3,839,400 sample bits and
3,830,868 transition-mask bits. Those verification-work counts include copies,
interfaces and outputs. They are not the number of unique learned gates or
physical FPGA nodes; the canonical gate denominator is 1,796,000 bit pairs.

## Explain the apparent discrepancies

For these 14 aligned observation buses, recorded-event counts equal settled
counts, with no unknown-involving changes inside those windows. There is no
NumPy-versus-settled-RTL discrepancy for this workload.

The earlier **1,843,155** whole-file diagnostic is a different quantity. It
includes clock/control, output-tree logic, duplicate layer views, bookkeeping
and reset/fill/drain. Even the whole-file canonical layer buses have 629,527
known flips and 3,772 unknown-involving changes; their aligned useful-image
comparison has 628,169 known flips and zero unknown-involving changes. The
opening image establishes baseline state instead of counting startup into it.
The counts use different populations and boundaries, so disagreement with a
software rate is expected until those definitions are matched.

If a bus changes and returns between two samples, its settled difference can
remain zero while the event counter records changes. X/Z excursions require
the separate unknown-involving field; known-event counts alone are incomplete
in their presence. Such recorded events are simulator behavior, not measured
physical glitches. This step checks settled agreement without erasing them.
Same-timestamp pulses cannot appear: Icarus writes each identifier at most
once per timestamp, so raw/settled agreement is not independent evidence.

Per-stage windows preserve the same image pairs but remain staggered physical
times. Adding their counts does not create a common device-energy interval.

## Debugging the test fixture

**Expected versus actual:** the first repeated-zero-input test assumed all 16
images would have tied class scores. The report and separate scalar/VCD oracle
both found zero ties, while the expected zero settled switching was correct.
The initial targeted run had 20 passing cases and one failing assertion in
1.31 seconds. No production mismatch was found.

**Reproduce the preserved original failure:**

```bash
PYTHONPATH=tests:scripts:. .venv/bin/python -m pytest \
  runs/step-3.7-verifier-debug/repeated-fixture-tie-assumption/initial-test_activity_numpy.py \
  -q -k repeated_zero
```

That folder preserves the original test/capture/comparison evidence and
`initial-observations.json`. The verifier re-ran this exact command and
confirmed the expected old `assert 0 == 16` failure. Complete output and
command/environment/status are in `archived-exact-reproduction.{txt,json}`;
`corrected-verification.json` records the passing expanded suite. This is an
intentional reproduction of the old test expectation error.

**Root cause and fix:** repeated inputs guarantee repeated outputs, but do not
guarantee equal scores across classes. Keep the repeated-input zero-change
test, and build a separate fresh Icarus fixture whose final layer is all
constant-zero gates. All class scores then equal zero; every image must
choose class 0. This makes the tie assertion explicit rather than relying on
random connections. Production code, NumPy reference and timing constraints
did not change.

**Verification and prevention:** the expanded independent suite passed all
22 cases in 1.35 seconds, no skips, including 16 explicit tied-score images
and the repeated-input zero-change case. Retain both tests so constancy and
ties remain separate properties. The independent review records the recheck.

## Bounded research assessment

- **Tested correctness:** settled layer values and exact transition masks match
  NumPy for these supplied images and register schedules, including scores and
  lowest-index ties. This is not formal equivalence over every possible input.
- **Measurement proxy:** the software logical-change metric agrees with this
  matched zero-delay RTL workload. It excludes mapped routing, capacitance,
  clock trees and physical glitches. Agreement does not validate `2p(1−p)`
  as a power estimator or show the penalty improves training.
- **Power/energy:** no device power estimate or electrical measurement, and no
  demonstrated energy saving. Steps 3.8–3.9 and 5.x require separate evidence.
- **Direction:** proceed to mapped activity in 3.8 and complementary metrics
  in 3.10, then matched validation-selected training. Keep target, architecture,
  clock, data splits and input sequence matched. Historical inspected digits
  results remain exploratory; research novelty remains unverified.
