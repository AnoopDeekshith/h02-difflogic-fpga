# Step 3.2: Verify waveform recording

Status: completed and independently verified. November 16, 2026.

## Why

Before counting switching, establish that the simulator can record the relevant
signals without changing inference results. A VCD (Value Change Dump) is a
timestamped record of simulated signal values, not a power measurement.

## What and how

The existing [core testbench generator](../../dlgn/export_verilog.py) includes
`$dumpfile("dlgn.vcd")` and `$dumpvars(0, dut)` under the `DUMP` definition.
[run_sim.sh](../../sim/run_sim.sh) enables it when the `DUMP` environment
variable is nonempty. Leave `DUMP` unset to disable it; `DUMP=0` also enables it.
No inference RTL or training settings were changed for this step.

Added [check_waveform_recording.py](../../scripts/check_waveform_recording.py):

1. Create a fresh attempt directory, retaining status even if checks fail.
2. Export the first eight saved inputs with fresh NumPy score/class references.
3. Run both recording modes on the original combinational core and the
   head-only pipelined core used within the feasible board candidate.
4. Require exact score/class PASS in every run; compare generated RTL,
   testbench, parameters and vector hashes across on/off modes.
5. Require no VCD when recording is off. When on, check completed definitions,
   timescale, advancing timestamps, expected bus widths and known observations.
   Clock, reset and valid signals must each show both states, and input data
   must change. Require inputs, outputs, `l0`, and every `lN`/`lN_c` layer bus.
6. Save commands, logs, model/input/source hashes and compiler/runtime identities.

This is a narrow observability check, not a general VCD validator. Unknown
startup values are allowed; counting/handling unknown transitions is step 3.4.
VCD identifiers can be aliases; no activity sum is computed here.

## Concrete example

A waveform might say `#5000` followed by `1!`: at timestamp 5000 the signal
whose identifier is `!` became one. The declaration tells us whether that is
the clock or another signal. Identifiers are local to each file; never assume
`!` always means clock.

Seeing a signal change establishes recording. To measure its switching rate,
we still need a defined useful-work window and a denominator, and to distinguish
settled logical outputs from simulator events. Those are later steps.

## Reproduce

From the repository root, with NumPy, Icarus `iverilog` and `vvp` installed:

```bash
.venv/bin/python scripts/check_waveform_recording.py runs/digits_w1000 --n 8
.venv/bin/python -m pytest tests/test_waveform_recording.py -q
```

The command prints a fresh `waveform-check.<suffix>/result.json` path. It does
not overwrite the historical model, saved inputs, or earlier simulations.
Generated runs remain gitignored, so a fresh clone needs the model/input artifacts.

decoded the saved input/score/class vectors against NumPy. Its 14 focused tests
pass: four on/off simulator cases across all register configurations and ten
inspector acceptance/fault cases. The final full suite passed **85 tests in
9.34 seconds**, no skips. No blocking finding remained in this recording scope.

## Viewing the waveform locally

**VS Code option:** installed
[VaporView](https://marketplace.visualstudio.com/items?itemName=lramseyer.vaporview)
1.6.1 on November 16 and opened the same head-only VCD in the existing project
window. Visually verified clock, reset, valid signals, input, all four layer
buses, predicted class and scores. Open the `.vcd` file in VS Code; double-click
signals under `tb_dlgn.dut` in the VaporView Netlist sidebar to add them.
This uses the same recorded data as Surfer, with no RTL or simulation change.

On this Mac, Surfer 0.6.0 and GTKWave were already installed; no additional
standalone viewer dependency was needed. Surfer successfully displayed the head-only
core's eight-image trace. Start with the clock, reset, input/output valid,
image input, layer buses, predicted class and packed scores. Only interpret
`class_out` and `scores` as predictions when reset is low and `out_valid` is high; unknown/red
values during startup are not valid inference outputs.

Reopen the saved local view from the repository root:

```bash
surfer --state-file runs/waveform-viewer/head-core-view.ron
```

Or load the original trace directly:

```bash
surfer runs/digits_w1000/waveform-check.njxy5prx/comb_head_dump_1/dlgn.vcd
```

The local view/command file and a macOS launcher are in
`runs/waveform-viewer/` (gitignored). The launcher is
`Surfer.app`, containing an unchanged copy of the installed Homebrew binary.
These local convenience files do not replace the tracked evidence above.
Surfer supports adding signals and fitting the time range through its
[documented commands](https://docs.surfer-project.org/book/commands/index.html).

Viewer-launch diagnosis: expected desktop control to open the installed viewer;
`getApp('/opt/homebrew/bin/surfer')` returned `Invalid app` because the Homebrew
installation is an executable rather than an app bundle. Direct `surfer <VCD>`
loaded successfully; a local app bundle made the same binary accessible to
desktop control. The complete signal view was then verified visually and
saved. Use the CLI or local bundle to avoid the same launcher issue. The
separate GTKWave desktop launch timed out; its underlying cause was not
established, and GTKWave is not the verified viewer in this setup.

## Limits and research direction

- **Tested correctness:** the recording-on/off runs both match their NumPy
  scores/classes on the selected inputs. This is not formal equivalence.
- **Measurement:** the bench uses its existing nominal 100 MHz functional
  clock. This is not the timing-qualified 12 MHz workload, a UART trace, or a
  full 450-image baseline capture. Step 3.3 must explicitly freeze architecture,
  clock and input/valid sequence. Do not use these smoke traces as matched
  power evidence.
- **Switching proxies:** the Python baseline and the training penalty remain
  different views of activity. This step computes neither waveform toggle
  totals nor settled-output/Python agreement. Fill/drain/reset exclusion,
  aliases and categories remain steps 3.4–3.7.
- **Power/energy:** no mapped-delay glitches, capacitance, device power or
  electrical measurements are established. There is no demonstrated energy saving.
- **Novelty:** recording is infrastructure. It does not establish that the
  switching regularizer is effective or novel. Continue conditionally with
  matched experiments and the feedback additions in the checklist.
- **Simulator scope:** trained-model recording is checked with Icarus only;
  Verilator and Vivado recording backends are not verified by this result.
