# Step 4.10: Prepare validation-only experiment selection

Status: complete; independently verified ([review](../reviews/step-4.10-independent-review.md)).
Recorded November 18, 2026.

## Why this comes before the penalty experiments

We need to choose penalty strengths without using the test set to guide that
choice. Training, validation and test data serve different purposes:

- **Training:** examples used to adjust the model's gate-choice weights.
- **Validation:** examples used to choose among trained models and settings.
- **Test:** evaluation after the model-selection decision has been recorded.

Think of validation as a practice exam and test as the final exam. Looking at
the final exam after every practice attempt makes it harder to claim that the
eventual score measures performance on unseen questions.

The historical `runs/digits_w1000` model monitored test results during training.
It remains a preserved exploratory baseline. The corrected trainer already
monitored validation, but still evaluated test at the end of every run. This
step adds a complete path for deferring that evaluation, saving the validation
workload and selecting using a rule fixed before training.

This is preparation for [4.3–4.5 in the checklist](../PROJECT_CHECKLIST.md),
not evidence that the penalty improves recognition, hardware switching or energy.

## What was implemented

[The trainer](../../scripts/train.py) now accepts `--defer-test` and
`--selection-policy`. In deferred mode it trains on the training split,
monitors validation and saves the final model with validation scores and
switching. It does not construct test tensors, run test inference or save test
inputs and labels. Test metric fields are explicitly `null`, and
`test_evaluated` is `false`.

The existing dataset loader still returns the dataset's test arrays, and the
run records the test-set size. Deferring test means withholding evaluation
and saved test artifacts; it does not mean the dataset has no test partition.

Without `--defer-test`, the compatibility mode still evaluates test and saves
its artifacts. Such a run is deliberately rejected by the validation selector.
New sweeps must use deferred mode for the control and every candidate.

[The selector](../../scripts/select_validation_models.py) checks archived
runs and chooses one model using only hard-model validation accuracy and
settled logical switching. [The later evaluator](../../scripts/evaluate_selected_model.py)
loads that selected checkpoint for a separate test evaluation, without retraining.

## The selection rule in plain language

The [versioned policy](../experiments/validation-selection-v1.json) permits
an accuracy loss of at most **one percentage point relative to the matched
zero-penalty control**. This is a working experimental tolerance. It is not a
professor requirement, an established optimum or an accuracy target in itself.
The policy is copied into each run before training. A different tolerance
requires a separately named policy and a separately documented experiment.

For a teaching example, suppose the control has 90 percent hard validation
accuracy. The floor is 89 percent. A candidate with 89.5 percent accuracy can
compete; one with 88.5 percent cannot, even if it switches much less.

Among eligible models, including the control, choose:

1. Lowest settled validation switching rate.
2. If tied, highest validation accuracy.
3. If still tied, lowest penalty strength, lambda.
4. Finally, the model's SHA-256 hash for a repeatable tie break.

The control is allowed to win. Selection does not assume that adding a penalty
must help. A hash is a fingerprint of file contents, not a quality score; its
last-place role simply removes ambiguity between otherwise tied records.

Every candidate is the **final epoch of the same fixed training budget**.
Validation history is saved, but this workflow does not select an earlier best
epoch or implement early stopping. The selector handles **one matched model
seed at a time**. Combining results across seeds remains a later experiment;
it does not pool seeds into a sweep and choose the luckiest initialization.

## How validation switching is measured

NumPy evaluates every learned gate on the saved validation inputs, in their
saved order. For each neighboring image pair, we count gate-output bits that
change. Divide the total by:

```text
number of learned gates × number of adjacent validation-image pairs
```

The digits protocol uses 1,077 training images and 270 validation images,
leaving the 450-image test partition separate. A four-layer, 1,000-gate model
therefore has `4000 × 269 = 1,076,000` validation bit-pair opportunities.
The first image establishes state; it is not an extra transition.

This measurement uses the **hard network's actual settled outputs**, whereas
training's activity penalty uses batch-mean soft outputs. They are different
quantities. Input order affects the measured rate, so preserving validation
order is part of the experiment. [Step 3.10](3.10-report-complementary-switching-metrics.md)
explains those distinctions and why neither quantity is energy.

## What gets saved and checked

Each new run directory contains the following records:

| Files | Purpose |
|---|---|
| `model.json` | Fixed gate rules and connections for NumPy and later RTL export |
| `checkpoint.pt` | Learned weights, optimizer state, PyTorch RNG state, completed epochs and arguments |
| `metrics.json` | Validation accuracy, exact change counts and denominator, score/class agreement and training history |
| `x_validation_bits.npy`, `y_validation.npy` | Exact ordered validation inputs and labels |
| `validation_scores.npy`, `validation_classes.npy` | NumPy integer scores and lowest-index-tie predictions |
| `split_indices.npz` | Training and validation indices into the original training pool |
| `protocol.json`, `selection_policy.json` | Configuration, versions, data identities, split/order description and predeclared policy |
| `manifest.json`, `status.json` | Source/artifact fingerprints and explicit running, failed or passed status |

The run reader verifies fingerprints and recomputes validation scores, classes,
accuracy and switching from the archived model and inputs. It checks that split
indices are disjoint and complete. Hard PyTorch scores, after undoing tau
scaling, and predicted classes must match NumPy. Ties retain the lowest class
index, as required by the golden reference.

The selector requires matched dataset, architecture, seed, split seed, training
budget, learning settings, device, data identities, versions and source-code
fingerprints. Penalty strength is the intended varying setting. Training source
hashes are checked again before sealing a run, so a code change during training
cannot silently produce a passed bundle. These fingerprints support provenance;
they do not replace preserving the source code and raw artifacts.

Existing output directories are rejected. Failed attempts retain failed status.
This keeps an old successful model from being overwritten or mistaken for a
successful new run.

## Commands using separate new directories

Run from the repository root. The following are examples for a future matched
60-epoch comparison, not results already obtained. Both output directories and
the selection filename must be new. Never write into `runs/digits_w1000`.

```bash
.venv/bin/python scripts/train.py --dataset digits \
  --width 1000 --depth 4 --tau 10 --epochs 60 --bs 100 --lr 0.01 \
  --seed 0 --split-seed 0 --device cpu --act-mode batch \
  --defer-test --act-weight 0 \
  --selection-policy docs/experiments/validation-selection-v1.json \
  --out runs/digits_selection_v1_seed0_control

.venv/bin/python scripts/train.py --dataset digits \
  --width 1000 --depth 4 --tau 10 --epochs 60 --bs 100 --lr 0.01 \
  --seed 0 --split-seed 0 --device cpu --act-mode batch \
  --defer-test --act-weight 0.1 \
  --selection-policy docs/experiments/validation-selection-v1.json \
  --out runs/digits_selection_v1_seed0_lambda01

.venv/bin/python scripts/select_validation_models.py \
  --control runs/digits_selection_v1_seed0_control \
  --candidates runs/digits_selection_v1_seed0_lambda01 \
  --policy docs/experiments/validation-selection-v1.json \
  --out runs/digits_selection_v1_seed0_selection.json
```

Only after selection is recorded, explicitly evaluate its chosen checkpoint:

```bash
.venv/bin/python scripts/evaluate_selected_model.py \
  --selection runs/digits_selection_v1_seed0_selection.json \
  --out runs/digits_selection_v1_seed0_test_evaluation
```

This command rechecks selection against the archived candidates, verifies code
and regenerated data identities, loads the checkpoint and confirms that its
hard gates/connections match the selected model. It then reports soft, hard
and NumPy test results, saves test inputs and reference outputs in the separate
evaluation directory, and preserves the training bundles. It does not train
another model. Once test results are inspected, they must not guide another
round of selection presented as if that test remained unseen.

## Mechanism evidence and current review status

The saved preparation run is
`runs/step4.10-preparation.20uuxoj6/`. It trained a lambda-zero control and a
lambda-0.1 candidate for **one epoch**, each with four layers of 1,000 gates.
Both used deferred test evaluation; their saved artifacts contain validation
data and null test metrics. The selection report chose the control. The
penalized candidate fell below the control-relative accuracy floor despite
having lower logical switching in this short check.

This is a mechanism check, not a meaningful trained-model comparison. One
epoch cannot establish the penalty's effectiveness or its accuracy tradeoff.
Commands, logs, run manifests and `selection.json` preserve what was attempted.
The full regression suite passes **285 tests in 19.18 seconds**, with no skips.
This includes the 255 pre-change cases, 23 validation-selection cases and
7 additional independent review cases. The initial 27-case focused command
included 4 pre-existing partition tests; those are not 27 additional new cases.
The [tracked summary](../results/step-4.10-validation-selection.json) preserves
the mechanism results and hashes. The [independent review](../reviews/step-4.10-independent-review.md)
records its separate scalar oracle, code/method checks and final documentation
review. Its final verdict is PASS, with no blocking finding.

The [focused tests](../../tests/test_validation_selection.py) exercise deferred
mode with test arrays that fail if accessed for inference, separate scalar
gate/count checks, artifact changes, existing-directory rejection, unmatched
runs, policy changes, accuracy-floor ordering, control selection and evaluation
without retraining. Run them with:

```bash
.venv/bin/python -m pytest tests/test_validation_selection.py -q
```

## Limits and research direction

**Correctness:** this prepares an auditable software selection mechanism.
The independent reviewer checked the code, methodology, every saved real-data
validation score/class and exact change totals. No blocking code finding was
identified. The final documentation and evidence recheck also passed.

**Measurement:** selection uses unweighted settled logical switching, not mapped
net capacitance, routed glitches, clock activity or physical energy. Each
selected model still needs its own RTL equivalence, resource, timing and activity
checks under matched FPGA target, architecture, clock and input schedule.

**Research:** no power/energy benefit or novelty is established. The previously
inspected digits test remains exploratory. Repeated-seed aggregation, meaningful
training budgets and broader datasets remain future work. The November 18
professor update encourages working toward a conference contribution; it does
not specify a venue, deadline, dataset or this one-percentage-point tolerance.
